웹 산출물을 사용자의 작업 맥락이 유지되는 앱 같은 사용 경험으로 구현해 줘.
기존 프로젝트라면 현재 기능과 데이터를 보존하며 개선하고, 신규 프로젝트라면 아래 목표에 필요한 기능부터 완성한다.

[작업 입력 — 아는 항목만 작성]
- 프로젝트명 / 작업 위치 또는 저장소:
- 신규 제작 / 기존 프로젝트 개선:
- 사용자와 해결할 문제:
- 주요 화면과 핵심 작업:
- 기존 RULE·기획서·디자인·참고 자료:
- 확정 기술스택·배포 환경·변경할 수 없는 조건:
- 데이터 저장 방식과 보존할 데이터:
- 디자인 방향 / 브랜드 / 선호·기피 요소:
- 대상 기기·브라우저 / 접근성 기준:
- 작업 범위: 설계만 / 구현·검증 / 문서화 / 커밋·푸시·배포
- 성능 목표·기간·기타 제약:

빈 입력을 확정 사실로 채우지 않는다. 기본 작업은 구현·검증과 로컬 문서화다. 사용자가 설계만 요청했다면 구현하지 않는다. 커밋·푸시·배포·외부 문서 변경은 이 대화에서 승인된 범위를 따른다. 일상적인 구현 선택은 이유를 설명하며 진행하고, 결과를 크게 바꾸는 미확정만 필요한 만큼 질문한다.

1. 목표와 범위를 먼저 정리한다

사용자가 검색·탐색·입력·저장할 때 전체 화면이 반복해서 초기화되는 문제를 해결한다.
‘앱처럼’이라는 표현을 다음 결과로 구체화한다.
- 작은 작업에는 영향을 받는 영역만 바뀐다.
- 목록 조건·입력·선택·스크롤·키보드 초점 등 필요한 맥락이 유지된다.
- 처리 중·성공·실패·결과 미확정을 구분할 수 있다.
- 주소 공유·새로고침·뒤로가기 등 웹의 기본 동작도 사용할 수 있다.

현재 동작을 코드와 실제 화면에서 확인하고, 목표·포함 범위·제외 범위·변경 이유를 짧게 설명한 뒤 진행한다. 사용자 확정사항, 원문 요구, 구현 제안, 미확정을 구분한다. 기존 ID와 의미를 보존한다. 예시 기능을 모두 새 기능으로 추가하지 않는다.

2. 화면별 전환 방식을 설계한다

각 핵심 작업에 ‘어느 영역이 바뀌고 어떤 상태를 유지하는지’를 정한다.
- 메뉴 이동: 공통 화면 틀을 유지하고 선택한 본문으로 전환한다.
- 검색·필터·정렬·페이지 이동: 결과와 관련 개수·선택 상태를 갱신한다.
- 상세 보기: 작업 특성에 맞춰 옆 패널, 본문 상세 영역 또는 독립 화면을 선택한다.
- 등록·수정: 내용의 길이와 복잡도에 맞는 폼·패널·화면을 사용한다.
- 즐겨찾기·상태·공유·선택 변경: 변경 결과가 영향을 주는 요소를 갱신한다.
- 삭제: 취소와 실제 삭제 결과를 구분하고 관련 목록·개수·선택 상태를 정리한다.
- 업로드·가져오기·긴 처리: 전송과 서버 처리, 완료 결과를 구분한다.

필터 변경 시 페이지를 초기화할지, 검색어를 유지할지 등은 기존 정책이나 사용자 목적에 맞춰 명시한다. 모든 버튼을 모달로 만들거나 모든 작업을 같은 패널에 넣지 않는다. 로그인·로그아웃·외부 링크·다운로드·배포 버전 전환 등 전체 이동이 필요한 경우는 따로 정의한다.

3. 검증 가능한 요구사항을 만든다

각 핵심 조건을 다음 구조로 정리한다.
ID / 출처·상위 목표 / 사전 상태·사건 / 보장할 결과 / 통과·실패 기준 / 증거 / 상태

조건이 필요한 문장은 ‘어떤 상태에서 어떤 사건이 발생하면 시스템은 어떤 관찰 가능한 결과를 보장해야 한다’는 EARS 방식으로 쓴다. 항상 적용되는 조건에 억지로 사건을 넣지 않는다.
하나의 조건에는 독립적으로 판정할 수 있는 의무를 두고, 여러 의무가 있으면 하위 ID로 나눈다. 기술 선택과 검사 절차는 요구 결과와 구분한다.

NASA 요구사항 품질 지침을 참고해 명확성·단일 의무·필요성·추적성·실현 가능성·검증 가능성·전체 일관성을 점검한다. 방법론을 적용했다는 이유로 요구사항이 완전하거나 구현이 성공했다고 주장하지 않는다.

4. 부분 갱신과 상태 관리를 구현한다

- 정상적인 작은 작업에서 전체 문서를 다시 불러오거나 공통 화면 틀을 매번 재생성하지 않는다.
- 서버가 있는 시스템에서는 저장·권한·업무 규칙의 최종 판정을 기존 서버에서 수행한다.
- 한 작업이 여러 영역에 영향을 주면 목록·개수·상세·집계 등 필요한 곳을 일관되게 갱신한다.
- 변경된 항목이 현재 필터에서 제외되거나 정렬 위치가 달라질 때의 표시를 정의한다.
- 마지막 행 삭제, 빈 결과, 유효 범위를 벗어난 페이지를 처리한다.
- 새 화면을 적용할 때 이벤트가 중복 등록되거나 타이머·구독·요청이 남지 않도록 정리한다.
- 화면 표시만 성공으로 바꾸고 실제 저장·권한·집계를 확인하지 않는 구현은 피한다.

저장 성공을 확인한 뒤 표시하는 방식을 기본으로 한다. 낙관적 갱신이 적합한 작업은 적용 이유, 실패 시 원복, 연속 작업과의 충돌 처리를 함께 정의한다.
서버가 없는 산출물은 로컬 저장·메모리·모의 데이터 중 무엇을 사용하는지 명확히 하고, 새로고침·기기 변경 시 보존 범위를 문서화한다. 시연용 저장을 실제 서버 저장으로 보고하지 않는다.

5. 주소와 탐색 이력을 일관되게 관리한다

- 공유할 필요가 있는 화면·필터·선택 항목은 주소로 재현할 수 있게 한다.
- 입력 중인 비밀번호나 임시 폼 데이터 등 주소에 넣으면 안 되는 상태는 URL에 기록하지 않는다.
- 뒤로가기·앞으로가기는 사용자가 이해할 수 있는 탐색 단계로 이동한다.
- 단순 토글·즐겨찾기·공유 변경마다 불필요한 이력을 추가하지 않는다.
- 목록에서 상세를 연 경우와 상세 주소로 직접 방문한 경우의 닫기·뒤로가기 동작을 구분한다.
- 패널을 닫으면 적절한 목록 조건·스크롤·시작 요소의 초점을 복원한다.
- 새로고침·새 탭·직접 링크·파일 다운로드와 필요한 기본 링크 동작을 유지한다.
- 취소한 이동은 주소와 화면 상태가 다시 일치해야 한다.
- 삭제됐거나 접근권한이 달라진 자료를 과거 화면 캐시만으로 다시 표시하지 않는다. 필요한 시점에 서버 상태를 재검증한다.

6. 느린 응답·실패·재시도를 설계한다

검색 A 다음 B를 선택했는데 A가 늦게 도착해도 최종 화면은 B여야 한다. 상세 선택, 필터 변경, 페이지 이동에도 같은 원칙을 적용한다.

변경 요청은 최소 다음 상태를 구분한다.
대기 → 처리 중 → 성공 / 실패 / 처리 여부 미확정

- 처리 중에는 해당 작업의 진행 상태를 알리고 같은 UI의 중복 제출을 막는다.
- 버튼 비활성화만으로 다른 탭이나 재시도까지 중복 처리가 방지된다고 주장하지 않는다. 업무상 중복 방지가 필요한 경우 서버의 멱등성·고유 제약·버전 검사 등 적절한 방법을 검토한다.
- 서버가 처리했지만 응답만 유실됐을 수 있는 요청을 무조건 자동 재전송하지 않는다.
- 미확정 결과는 서버 상태를 확인할 수 있는 경로를 제공한다. 조회 자체가 실패하면 다시 조회할 수 있어야 한다.
- 복구 조회 때 기존 필터가 새로 저장된 항목을 숨겨 잘못된 결론을 만들지 않도록 한다.
- 검증 오류와 네트워크 오류는 입력을 가능한 범위에서 보존하고 작업 위치에서 안내한다.
- 파일 입력은 새로고침·이동 뒤 복원할 수 없는 경우 재선택 필요성을 안내한다.
- 저장되지 않은 입력을 버리는 이동에는 확인을 제공한다.
- 업로드 전송 100%와 최종 저장 완료를 구분한다.
- 시간 초과·오프라인·로그인 만료·권한 거부 응답을 정상 콘텐츠나 성공 상태로 표시하지 않는다.
- 여러 사용자나 탭의 동시 수정이 실제 범위에 포함되면 충돌 발견·사용자 선택·재조회 정책을 정의한다.

7. 디자인과 접근성을 함께 구현한다

기존 브랜드와 승인된 디자인을 유지한다. 별도 방향이 없다면 읽기 쉬운 글꼴·명확한 위계·충분한 여백·부드러운 형태와 절제된 전환을 기본안으로 제안한다. 귀여운 테마·특정 색상·특정 글꼴은 모든 프로젝트에 강제하지 않는다.

- 데스크톱·모바일에서 작업에 필요한 공간과 조작 크기를 확보한다.
- 키보드 초점 이동·복귀·탐색 순서와 패널 닫기를 설계한다.
- 모달을 사용한다면 적절한 접근성 이름과 초점 범위를 제공한다.
- 동작 줄이기 설정을 지원하고 상태를 애니메이션이나 색만으로 전달하지 않는다.
- 성공·실패 알림이 버튼·입력·주요 콘텐츠를 덮어 조작을 방해하지 않게 한다.
- 로딩 중에도 필요한 화면 맥락을 유지하고, 빈 상태·실패 상태에는 다음 행동을 제공한다.
- 신규 폰트·아이콘·라이브러리를 추가하면 필요성·라이선스·로딩·대체 동작을 확인한다.

애니메이션 시간과 패널 너비는 구현 선택으로 구분한다. ‘빠르다·자연스럽다’는 주장만으로 완료 판정하지 않는다. 성능 목표가 필요한 경우 환경·측정 방법과 함께 정하고, 임의의 수치를 사용자 확정 목표로 만들지 않는다.

8. 기존 기능과 배포 호환성을 보존한다

기술 방식은 기존 구조, 데이터 수명, 상호작용 복잡도에 맞춰 선택한다. 서버 렌더링과 부분 HTML 갱신, 기존 프레임워크의 라우팅·컴포넌트 갱신 등 가능한 방식 중 변경 비용과 유지보수성을 설명한다. 특정 프레임워크나 별도 API 서버로의 전면 교체를 전제로 시작하지 않는다.

- 기존 데이터·업무 규칙·인증·권한·입력 처리·감사기록을 보존한다.
- UI 개선을 이유로 기존 정책을 완화하거나 새로운 정책을 몰래 추가하지 않는다.
- 인증·권한 변화가 다음 요청과 화면에 적절히 반영되도록 한다.
- 사용자 입력을 부분 렌더링할 때 기존의 출력 처리·인코딩·스크립트 실행 정책을 유지한다. 기능 검증을 위해 임의로 입력을 실행 코드로 취급하지 않는다.
- 기존 정적 자산의 버전 관리와 호환성을 유지한다.
- 과거에 사이트를 사용한 브라우저에서 오래된 JS·CSS와 새 화면이 섞이는 경우도 검사한다.
- 버전 변경으로 전체 이동이 필요한 경우 미저장 입력과 진행 중인 변경 요청의 처리 방법을 정의한다.
- 새로고침 때 데이터가 사라지거나 모의 데이터를 매번 다시 만드는 문제를 확인한다.
- 접근성·검색 노출·직접 링크·JavaScript 비활성 경로는 프로젝트의 기존 요구와 지원 범위에 맞춰 보존한다.

앱 같은 상호작용만으로 설치형 PWA, 오프라인 동작, 푸시 알림, 실시간 협업을 자동으로 추가하지 않는다. 이런 기능이 필요하면 별도 요구사항으로 다룬다.

9. 실제 동작과 반례로 검증한다

핵심 검사를 Given–When–Then으로 작성하고 요구사항 ID에 연결한다.
프로젝트에 해당하는 최소 사례를 선정해 실제로 실행한다.

- 정상 메뉴 이동·검색·필터·정렬·페이지 변경·상세 열기와 닫기
- 등록·수정·삭제 취소와 성공·공유·상태 변경 중 실제 기능
- 입력 오류·빈 결과·마지막 행 삭제·현재 필터에서 벗어난 변경
- 일부러 뒤집은 응답 순서와 빠른 연속 선택
- 저장 전 실패와 서버 처리 후 응답 유실
- 중복 클릭·재시도·필요한 동시 수정
- 뒤/앞 이동·새로고침·새 탭·직접 링크·다운로드
- 미저장 입력이 있는 이동과 이동 취소
- 세션 만료·권한 변경 뒤의 재검증
- 모바일·키보드·동작 줄이기
- 기존 자산 캐시·새 배포 버전 전환
- 전체 문서 탐색·공통 요소 재생성·중복 이벤트 여부

다음 반례로 구현을 검토한다.
‘이 요구사항의 문구는 지켰지만 사용자의 목적에는 실패하는 구현이 가능한가?’

예를 들어 전체 이동을 애니메이션으로 감추기, 저장 실패를 성공 버튼으로 표시하기, 옛 응답이 최신 화면을 덮기, 알림이 다음 버튼을 가리기, 중복 요청으로 실제 기록이 늘기, 복구 조회의 필터 때문에 저장 결과를 못 찾기 등을 살핀다.

기능에 필요한 서버/API 검사와 브라우저 검사를 선택하고, 실제 요청·응답·저장 상태·화면을 연결한다. 화면 캡처만으로 저장·권한 검증을 대신하지 않는다. URL 변경 이벤트가 발생한 사실만으로 전체 문서 재로드라고 단정하지 말고 실제 탐색 요청과 실행 문맥을 확인한다.

기존 데이터가 있는 경우 분리된 테스트 환경이나 식별 가능한 테스트 자료를 사용한다. 종료 시 자신이 만든 자료를 정확히 정리하고 남은 변경을 기록한다. 문제와 관련 없는 테스트를 불필요하게 늘리지 않는다.

10. 작업을 완료하고 근거를 전달한다

구현 단계:
현재 상태 확인 → 요구사항과 전환 설계 → 주요 흐름 구현 → 상태·오류·탐색 보완 → 기존 기능 회귀 검사 → 실제 화면 확인 → 문서화

한 화면만 구현한 뒤 전체 범위를 완료했다고 보고하지 않는다. 핵심 미확정이 있으면 그 부분을 명시하고 답변과 무관한 작업은 계속한다.

최종 산출물:
- 구현 코드와 실행 방법
- 요구사항 ID ↔ 변경 위치 ↔ 테스트 ↔ 결과 연결표
- 실제 화면과 주요 전환·저장 동작의 증거
- 기존 기능·데이터·정책의 유지 여부
- 발견한 반례와 수정한 내용
- 미실행 검사·지원하지 않는 환경·남은 제한
- 복구·되돌리기 방법
- 커밋·푸시·배포·외부 문서 반영 상태

실행한 검증과 추론, 사용자 사용성 평가를 구분한다. 실제로 하지 않은 시험·독립 검토·배포를 완료했다고 쓰지 않는다. 문서에 민감한 인증 정보나 세션 값을 불필요하게 포함하지 않는다.
