**정교한 조건은 실패하는 사례를 구분할 수 있어야 한다.**
## Given–When–Then
- **Given:** 어떤 데이터·상태에서 시작하는가?
- **When:** 무엇을 실행하는가?
- **Then:** 어떤 결과가 보여야 하는가?
다이어리 설명 예시: 진행 중인 할 일과 집계를 기록하고 → 같은 완료 주기의 두 요청을 겹쳐 실행하고 → 완료 사건 1건과 현재 완료 수 +1을 각각 확인한다. 이는 검사 설계 예시이며 이번 학습 정리에서 실행한 검사가 아니다. [Cucumber 공식 문법](https://cucumber.io/docs/gherkin/reference/)
## 가장 유용한 반례 질문
> 이 조건의 문구는 지켰지만 사용자의 목적에는 실패하는 구현을 찾아줘.
예: 버튼만 잠가 두 클릭을 막았지만, 다른 탭의 요청으로 완료 기록이 중복되는 구현. 화면 동작뿐 아니라 DB 기록과 집계를 확인해야 차이를 발견할 수 있다.
## 필요한 경우만 넓혀 보기
정상 → 빈 값·경계 → 재시도·동시 요청 → 실패·복구 → 접근 권한·시간대. 기능과 관계없는 경우를 억지로 추가하지 않는다.
완료 → 되돌리기 → 재완료처럼 상태가 바뀌면 **현재 완료 수와 과거 완료 사건 수를 분리**해 생각한다. 기존 PDS RULE의 설명이며 새 정책을 정한 것은 아니다.
## 무엇을 검증하는지 구분
- **요구대로 만들었는가:** 저장 값·집계·상태 전이 등을 검사한다.
- **사용자 목적에 도움이 되는가:** 실제 돌아보기 결론이 다음 계획에 활용되는지 살핀다.
사용자 실제 기록과 판단은 AI가 대신 만들어 통과시킬 수 없다.
