# 05 · AI로 명세 작성·검토

[Notion 문서](https://app.notion.com/p/3d60def9f626815ca350fb3732b46595?pvs=204)

<mention-page url="https://app.notion.com/p/3d60def9f62681c2bca2cf1e7c4263f6"/>
**하나의 프롬프트로 시작할 수 있지만, 좋은 결과에는 출처·질문·검사·반례 검토가 필요하다.**
## 기본 흐름
1. 원문·고정 결정·좋은 명세 예시를 제공한다.
2. 목표와 범위를 확인하고 중요한 미확정을 질문한다.
3. 조건을 ID·출처·결과·검사와 함께 작성한다.
4. 문구를 지켜도 목적에 실패하는 반례를 찾는다.
5. 근거 있는 지적만 반영하고 미결정을 남긴다.
이는 조사에 근거한 추천 절차이며, 모든 작업에 가장 우수하다고 검증된 방법은 아니다.
## AI끼리 경쟁시키면 더 좋은가?
항상 그렇지는 않다. 기본은 한 모델의 단계별 작성·검토다. 추가 검토가 필요하다면 **작성자 1명 + 독립 검토자 2명**을 선택적으로 비교할 수 있다.
| 역할 | 검토 범위 |
| --- | --- |
| 작성자 | 목표·조건·검사 초안 작성 |
| 검토자 A | 원문 누락·범위 확대·미확정 판단 |
| 검토자 B | 상태·동시성·시간·실패·복구 반례 |
| 통합 | 출처·반례로 채택/기각 이유를 남김 |
검토자는 초안을 보기 전에 같은 원문으로 필요한 조건을 독립적으로 생각하게 할 수 있다. 한 채팅에서 역할을 바꾸는 것은 별도 문맥의 독립 검토와 다르다. **다수결·자신감·조건 개수로 정답을 정하지 않는다.**
## 근거가 말해 주는 범위
- 요구 표현 연구: LLM 수정문에 대한 사용자 평가 개선을 관찰했다. 객관적 완전성이나 실제 구현 성공의 증명은 아니다. [2026 연구](https://arxiv.org/html/2601.16699v1)
- 토론 연구: 일부 NLP 벤치마크에서 다수결이 토론 성능 향상의 상당 부분을 설명했다. 요구사항 작성에 대한 직접 비교는 아니다. [Debate or Vote](https://arxiv.org/html/2508.17536v2)
- 긴 토론이 문제에서 벗어나는 현상도 보고됐다. 모든 다중 검토가 실패한다는 뜻은 아니다. [Stay Focused](https://aclanthology.org/2026.findings-eacl.268/)
## 우리 작업에서 비교하는 방법
같은 입력·모델·총 시간/토큰 상한으로 **A 단순 요청 / B 단계별 절차 / C 독립 검토 추가**를 비교한다. 원문 누락·근거 없는 추가·충돌·검사 불가능·핵심 미확정 발견과 비용을 사람이 평가한다. 평가용 작업을 프롬프트 예시와 분리한다. [작업별 평가 원칙](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
이 비교 실험과 다중 AI 실행은 아직 하지 않았다.
<details>
<summary>복사해서 쓰는 요청문</summary>
	내 아이디어를 구현 전에 검증 가능한 목표와 요구사항으로 정리해 줘.
	입력: 아이디어·사용자·문제 / 기존 조건과 고정 결정 / 환경·예산·기간·공개 범위 / 좋은 명세 예시.
	1. 목적과 사용자에게 생길 변화, 성공을 관찰할 방법, 범위를 먼저 정리한다.
	2. 원문·사용자 확정·AI 제안·미확정을 구분하고 기존 ID와 의미를 보존한다.
	3. 중요한 미확정은 한 번에 최대 3개 질문한다. 답과 무관한 작업은 계속하고 수치·정책·사용자 판단을 만들어 확정하지 않는다.
	4. 각 조건에 ID / 출처·상위 목표 / 상태·사건 / 보장할 결과 / 통과·실패 / 증거 / 상태를 붙이고 하나의 검증 가능한 의무를 둔다.
	5. 관련 있는 정상·경계·빈 값·재시도·동시 요청·실패·복구·권한·시간대를 살핀다.
	6. 문구는 지켰지만 목적에 실패하는 반례로 핵심 조건을 보완한다.
	7. 누락·충돌·근거 없는 추가·모호함·검사 불가능·과도한 구현 제한을 검토한다. 비판에도 원문이나 반례를 붙인다.
	8. 미승인 제안을 필수 RULE로 바꾸지 않는다. 실제로 하지 않은 독립 검토나 시험을 했다고 보고하지 않는다.
	출력: 목표 요약 → 조건표 → 검증 시나리오 → 원문 추적표 → 미결정 질문 → 검토에서 바뀐 점. 한 모델 안에서 작성과 검토를 구분하고, 독립 검토의 필요성은 별도로 제안한다.
