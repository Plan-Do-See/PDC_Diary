# 공통 메뉴 전환과 계획 카드 애니메이션

2026-09-11 사용자 확정: Plan·Do·See 메뉴의 전체 새로고침을 없애고 계획 제목 영역의 펼침·접힘에 애니메이션을 추가한다. 실제 웹의 로컬 구현·검증 범위다.

## 근거와 구현

- 관찰: 메뉴가 일반 a 링크였고 Plan 레이아웃과 Do/See 페이지가 각각 Workspace를 생성했다. 기존 details/summary는 즉시 열고 닫았으며 화살표에만 전환 효과가 있었다.
- 적용 출처: RULES.md와 요구사항 원문44/번호 없는18, 현재 pds-design.md·plan-disclosure.md, 사용자 app-like-interaction-guidelines.txt, 웹 AGENTS.md, DB 계약 list_contract/manual_order와 공개/개인 접근 경계, 설치된 Next.js의 Link·useLinkStatus·Layouts and Pages·Route Groups 원문.
- 메뉴: 기존 주소는 유지하고 웹 app/(diary) 공통 레이아웃에 WorkspaceFrame을 둔다. Plan·Do·See는 Next Link로 본문을 전환한다. 메뉴·main DOM과 문서 실행 문맥을 유지하고 활성 메뉴, 대기 표시, 브라우저 뒤로/앞으로 이동을 연결한다. 요청자 세션별 서버 조회/no-store/개인 requireAccount·PrivateGate는 유지하며 API/DB 계약은 변경하지 않는다.
- 카드: useAnimatedDisclosure가 실제 시작/목표 높이를 측정해 240ms 동안 전환한다. 접힘이 끝날 때 details를 닫으며 자식 폼·DND 컴포넌트는 제거하지 않는다. 연속 클릭은 현재 높이에서 반전하고 종료 후 고정 높이를 해제한다. 크기 변경 또는 동작 줄이기 변경 중에는 목표 상태로 마무리한다. 동작 줄이기에서는 즉시 전환한다.
- 인라인 할 일의 미저장 입력/처리 중·미확정 상태에서 메뉴를 누르면 떠나기 확인을 제공한다. 취소하면 입력과 펼침을 유지한다. 저장 후 남겨 두는 기본값은 미저장 입력으로 취급하지 않는다. 별도 저장소나 전역 사용자 데이터 캐시는 추가하지 않았다.

기존 PC-01~09 회귀도 통과: 입력·카드/리스트·직접 주소·키보드·명시적 상세 복귀·DND 저장 후 부분 갱신을 확인했다. 합성 계획의 순서를 바꾼 뒤 원래 순서로 복구했으며 새 자료·운영 기록은 만들지 않았다. 버전은 정상 저장 규칙에 따라 증가했다. 타입·기존 단위21·Windows 빌드 통과. 첫 빌드의 옛 개발 타입 파일 경로 오류는 생성된 validator.ts를 제거해 해소했고, 첫 직접 주소 시험의 header 개수 오류는 See 본문 header까지 세던 검사 선택자를 공통 메뉴/main으로 좁혀 교정했다.

## 경계와 남은 일

- 이번 메뉴 이동을 승인하면 떠나는 페이지의 임시 입력을 폐기한다. 전 페이지의 미저장 입력 보호, 페이지별 입력/스크롤의 자동 영속 보관을 구현한 것으로 표시하지 않는다. 확인 창은 이번에 관련된 인라인 할 일과 세 메뉴에 적용된다.
- 크기/동작 줄이기 설정의 전환 도중 변경 처리 코드는 있으나 해당 도중 변경의 별도 브라우저 검사는 미실행이다. 로그인된 개인 계정에서 메뉴 전환은 이번에 별도 시험하지 않았다. 비로그인 개인 접근 차단과 기존 서버 인증 경로 보존만 확인했다.
- JavaScript를 끈 전체 페이지는 이전과 동일한 Next 스트리밍 숨김 영역으로 조작되지 않았다. 이를 통과로 세지 않는다. Figma 제외·소셜 보류·PDF 제외·실제 사용자1/5/3 및 전체 과제 인수 미완료를 유지한다.
- 푸시·배포는 실행하지 않았다. 이전 업로드 승인 대기와 배포 묶음 재생성 필요 상태를 유지한다. 현재 확인 주소는 http://127.0.0.1:3104/plans 이다.
- 복구: 공통 레이아웃/경로 이동과 메뉴 Link·애니메이션 훅·인라인 이동 확인 변경을 되돌린다. 기존 DB 스키마나 기록 복원은 필요하지 않다.

## 2026-09-11 · 메뉴 로딩 화면 깜빡임 보완

이전 NM 검사는 문서 새로고침0만 확인했고 큰 loading 화면으로 본문이 바뀌는 현상을 놓쳤다. 사용자 후속 지적으로 원문 RULE·현재 설계·웹 AGENTS·설치된 Next loading.js 원문을 다시 확인했다. plans와 catch-all의 loading.tsx 두 경계를 제거하여 다음 본문이 준비될 때까지 현재 본문을 유지한다. 메뉴의 작은 대기 표시·오류 처리·기존 URL/no-store/인증/API/DB 계약은 유지한다. 초기 직접 주소는 서버 응답을 기다리며 이번에는 별도 페이지 skeleton을 두지 않는다.

동일 메뉴5회, RSC 요청500ms 지연의 실제 브라우저 비교: 수정 전172개 화면 표본 중75개에서 큰 로딩 화면/제목 공백, 수정 후195개 표본 중0개. 전후 main 유지·문서 요청0, 조작 전4초 유휴 요청0. LT-01 본문 유지, LT-02 문서 요청0, LT-03 관찰 구간 유휴 요청0, LT-04 기존 NM11 회귀 모두 통과. Windows 타입/빌드 통과. 증거는 loading-transition-verification.json. 읽기 전용 검사이며 POST·실제 기록 변경0이다.

데이터는 메뉴 진입 때 최신 조회하며 계획별 DND 순서 조회도 남아 있다. 요청 수/캐시 최적화를 완료했다고 주장하지 않는다. 현재 관찰에서 자동 반복 요청은 없었지만 무기한 유휴를 검증한 것은 아니다. 노션02/10 재조회 완료, 로컬 반영이며 푸시·배포는 하지 않았다. 복구는 제거한 두 loading.tsx를 복원하는 것으로 가능하다.
