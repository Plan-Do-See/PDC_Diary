# 정교한 목표·제약조건을 만드는 방법 — 조사와 제안

2026-09-09 · **연구 기반 AI 제안**. 이번 요청은 방법 조사와 전달이다. 기존 RULE·44개 인수 조건·구현 계약은 변경하지 않는다. 아래 절차의 보편적 최적성이나 실제 프로젝트의 품질 향상을 실험으로 확인한 것은 아니다.

## 조사 결론

추천 조합은 **좋은 예시와 출력 형식 + 목표 확인 질문 + 상태·예외 분석 + 조건별 검사 설계 + 독립적인 반례 검토**다. 하나의 프롬프트로 절차를 시작할 수 있지만, 미확정 요구의 답변과 검사 근거까지 자동으로 만들어 확정해서는 안 된다.

정교함은 필요한 목표에 연결되어 있고, 해석이 일관되며, 통과/실패를 관찰할 수 있는지를 기준으로 판단한다. 근거 없이 조건이나 기술 제한을 추가하지 않는다.

## 적용 절차

1. **입력·출처 고정:** 사용자 원문과 ID, 채택된 결정, 실제 환경·기한·예산, 좋은 조건의 예시를 모은다. 사실·사용자 확정·AI 도출·미확정을 나눈다.
2. **목표 구체화:** 누구의 어떤 문제가 어떻게 달라져야 하는지, 그 변화를 어떻게 관찰할지 정한다. 목표 달성과 기능 구현을 각각 확인한다. 수치가 필요하지만 근거가 없으면 미확정으로 남긴다.
3. **작동 모델 작성:** 핵심 상태·사건·데이터·역할을 표로 정리한다. 관련 있는 빈 값·경계·중복·동시성·실패·복구·권한·시간대 경우를 점검한다.
4. **조건을 검사와 함께 작성:** ID → 원문/목표 → 발동 조건 → 보장할 결과 → 통과/실패 → 증거를 연결한다. 구현 선택은 별도에 두고 이미 확정된 기술 제약은 보존한다.
5. **반례 검토:** “문구는 지켰지만 목적에 실패하는 구현”을 찾아낸다. 각 지적에는 관련 조건과 구체적 반례 또는 원문 충돌을 요구한다.
6. **통합과 판정:** 누락·중복·충돌·과도한 제한을 정리하고 추가 제안의 채택 여부를 구분한다. 중요 미확정이 남으면 초안으로 표시한다. 정해진 검토 예산 뒤에도 남은 문제는 보고한다.

설명을 위해 만든 한국어 EARS 적용 형태: **[사전 상태]에서 [사건]이 발생하면, [시스템]은 [관찰 가능한 결과]를 보장해야 한다.**

Given–When–Then은 사전 상태·행동·관찰 결과로 구체적인 검사 시나리오를 표현하는 데 쓴다. 도구 설치가 먼저 필요한 것은 아니다. [Cucumber 공식 문법](https://cucumber.io/docs/gherkin/reference/)

## 다이어리의 완료 처리를 예로 들면

기존 T06-C21/C22와 중앙 RULES의 완료 주기를 풀어쓴 설명이다. 새 필수 조건을 추가하거나 이번에 시험을 실행한 결과가 아니다.

| 항목 | 설명 |
| --- | --- |
| 목적 | 중복 완료로 기록과 돌아보기 집계가 부풀지 않음 |
| T06-C21의 결과 | 같은 할 일·같은 완료 주기의 최초 완료 요청이 겹쳐도 완료 사건은 1건 |
| T06-C22의 결과 | 그 처리로 현재 완료 할 일 수는 1만 증가 |
| 검사 구성 | 진행 중인 할 일과 집계를 기록하고, 같은 주기의 두 완료 요청을 겹쳐 실행한 뒤 사건 수와 집계를 각각 비교 |
| 반례 | 버튼만 잠갔지만 다른 탭이나 직접 요청으로 완료 기록이 중복되는 구현 |
| 후속 경계 | 완료 되돌리기 후 재완료는 새 주기이며, 현재 완료 수와 과거 완료 사건 수를 구분 |
| 증거 | 요청 조건, 전후 DB 기록·집계, 관련 조건 ID, 실행 시각 |

목표의 예는 “돌아보기에서 얻은 한 줄이 다음 계획에 실제로 이어진다”처럼 사용자에게 생길 결과다. 원래 과제의 실제 사용자 기록과 판단은 AI가 만들어 대체할 수 없다.

## 여러 AI를 쓸 때

기본 구성은 한 모델의 단계별 작성·검토다. 독립 검토가 필요한 경우의 제안은 **작성자 1명 + 검토자 2명**이다. 이 연구 작업에서 에이전트를 생성하거나 경쟁시킨 것은 아니다.

- 검토자 A: 원문과 목표에 비춰 누락·범위 확대·사용자 미확정을 찾는다.
- 검토자 B: 상태·동시성·시간·실패/복구·검증 방법의 반례를 찾는다.
- 초안을 보기 전에 각 검토자가 같은 원문으로 필요한 범위와 위험을 독립적으로 적게 할 수 있다. 이후 초안을 보여 주고 차이를 근거와 함께 검토한다.
- 작성자는 근거 있는 지적만 반영하고, 채택/기각 이유와 미결정을 남긴다. 다수결이나 AI의 자신감을 진실의 판정 기준으로 삼지 않는다.
- 다른 모델은 추가 관점을 줄 수 있지만 오류가 독립이라는 보장은 없다. 한 대화에서 역할만 나누는 것은 별도 문맥의 독립 검토와 구분한다.

## 더 엄격한 검증

동시성·완료 주기·접근 제어처럼 핵심 규칙이 복잡해지면 상태 전이표와 항상 유지되어야 하는 식을 먼저 작성한다. 필요하면 TLA+/TLC처럼 상태 모델을 검사하는 도구로 반례를 찾는다. 검사 결과의 범위는 모델·가정·탐색 범위에 한정되며, 실제 구현과 목표의 적합성은 별도 검증한다. 전체 프로젝트에 즉시 도입하라는 뜻은 아니다. [TLA+ 원저자 설명](https://lamport.azurewebsites.net/tla/high-level-view.html)

## 어떤 방식이 좋은지 비교하는 최소 실험 제안

같은 초안·자료·모델과 총 토큰/시간 상한을 정하고 A: 단순 요청, B: 단계별 명세 절차, C: B+독립 검토를 비교한다. 소수의 대표 작업을 반복하고 원문을 아는 사람이 방식 이름을 가린 결과를 검토한다. 좋은 예시로 넣은 문서를 그대로 정답 시험에 쓰지 않는다.

평가 항목은 **원문 누락, 근거 없는 추가/변경, 서로 충돌하는 조건, 검사 불가능한 조건, 핵심 미확정의 발견**과 소요 비용/시간이다. 주어지지 않은 정책을 임의로 맞힌 것을 높은 품질로 평가하지 않는다. 원래 44개를 유지하는 작업이라면 44개가 모두 추적되는지 별도 확인한다. 조건 개수나 AI 자기 점수만으로 순위를 정하지 않는다.

이 비교는 제안이며 이번에 실행하지 않았다. 단일 모델보다 다중 검토가 이 프로젝트에서 우수한지는 미확정이다.

## 재사용 프롬프트

내 아이디어를 구현 전에 검증 가능한 목표와 요구사항으로 정리해 줘.

입력
- 아이디어·사용자·해결할 문제: [입력]
- 기존 조건과 변경하면 안 되는 결정: [원문 또는 경로]
- 환경·예산·기간·공개 범위: [입력]
- 원하는 명세의 좋은 예: [예시]

진행 규칙
1. 목적, 사용자에게 생길 변화, 성공을 관찰할 방법, 범위를 먼저 정리한다.
2. 원문 요구, 사용자 확정, AI 도출 제안, 미확정을 구분한다. 원문의 ID와 의미를 보존한다.
3. 목표·범위를 바꾸는 정보가 부족하면 영향이 큰 질문을 한 번에 최대 3개 한다. 답과 무관한 부분은 계속 작성한다. 수치·정책·사용자 판단을 만들어 확정하지 않는다.
4. 목표 → 기능 → 원자적 조건 → 검증 방법 → 증거를 연결한다.
5. 각 조건에 ID / 출처·상위 목표 / 사전 상태·발동 사건 / 시스템이 보장할 결과 / 통과·실패 기준 / 증거 / 상태를 적는다. 한 조건에는 하나의 검증 가능한 의무를 둔다.
6. 관련 있는 정상·경계·빈 값·재시도·동시 요청·실패·복구·권한·시간대 상황을 점검한다. 적용되지 않는 항목은 이유와 함께 제외한다.
7. 각 핵심 조건에 대해 “문구는 지켰지만 목적에는 실패하는 사례”를 만들고 조건이나 검사를 보완한다.
8. 원문 누락, 충돌, 근거 없는 추가, 모호한 말, 검사 불가능, 불필요한 구현 제한을 검토한다. 비판도 원문이나 구체적 반례로 입증한다.
9. 구현 방법과 요구사항을 구분하되 사용자가 이미 정한 기술 제약은 보존한다. 미승인 제안은 필수 RULE로 승격하지 않는다.
10. 최종 결과는 목표 요약 / 조건표 / 검증 시나리오 / 원문 추적표 / 미결정 질문 / 검토에서 바뀐 점 순서로 컴팩트하게 작성한다. 남은 문제를 숨기거나 완전성을 보장하지 않는다.

한 모델로 작성과 검토를 구분해 진행하라. 독립 에이전트가 실제로 필요한지와 추가로 확인할 항목은 제안하되, 역할을 나눠 썼다는 것만으로 독립 검토를 실행했다고 보고하지 마라.

## 작업 기록

- 요청: 정교한 목표와 제약조건을 생성하도록 AI를 사용하는 기술 조사.
- 확인: NASA/EARS 공식 설명, 요구 표현 연구 및 토론 연구의 본문·한계, Cucumber·OpenAI·TLA+ 공식 자료.
- 작성: 단계별 절차, 다이어리 조건의 설명 예시, 독립 검토 구성, 비교 실험안, 재사용 프롬프트.
- 상태: 연구 제안만 문서/노션에 기록. 기존 필수 RULE·44개 요구·제품 코드·계약을 수정하지 않았다. 다중 AI 실행·벤치마크·형식 검증·사용자 개인 판단 생성은 하지 않았다.
