## 실행 순서

1. 승인된 코드 브랜치와 배포 묶음을 전송한다. 웹은 서버에서 기존 Dockerfile로 Linux 이미지를 빌드하고, API는 로컬에서 만든 Linux/amd64 Jib 이미지를 불러온다. SHA·사용자·이미지 구성을 대조한다. 이때 운영 컨테이너는 교체하지 않는다.
2. 기존 설정·이미지 ID를 보관하고 잠깐 점검 화면을 적용한다. 기존 API의 작업을 멈춘 뒤 일관된 DB 백업과 표별 원본 열·행 비교 근거를 서버 안에 보관한다. 기존 API의 할 일 INSERT는 위치 열을 추가한 V4와 호환되지 않으므로 API를 계속 실행하면서 migration하지 않는다.
3. 새 API 이미지의 migration 전용 계정으로 V4만 추가 적용한다. 기존 열·행이 보존됐는지 대조하고 `pds_app`에 `plan_task_orders` INSERT/UPDATE만 추가한다. 계획 이력의 UPDATE 권한은 추가하지 않는다. 새 API·웹의 내부 읽기·건강 상태·순서 조회를 확인한 뒤 점검 화면을 해제한다. Swagger/연동 안내도 API0.3.0으로 맞춘다.
4. 비로그인 운영 읽기 검사로 Plan/Do/See/로그인·모바일 배치·순서 조회·개인 접근 경계를 확인한다. 실제 계획이나 순서를 바꾸는 운영 시험은 하지 않는다. 결과와 배포 ID를 로컬·노션에 기록한다.

## 실패 시 처리

- 빌드나 전송 검증 실패: 기존 운영을 유지한다.
- migration 또는 내부 확인 실패: 점검 화면을 유지하며 새 API의 쓰기를 중단한다. 보관한 DB 백업·이전 이미지로 복원하고 데이터 대조 및 기존 API 확인 후 서비스를 연다. DB 복원 대상·백업 시각·트래픽 차단을 확인하지 않고 덮어쓰지 않는다.
- 점검 해제 뒤의 문제: 새로 들어온 기록을 보존해야 하므로 과거 백업으로 자동 덮어쓰지 않는다. 우선 증거를 보관하고 문제 범위에 맞춰 복구한다.
